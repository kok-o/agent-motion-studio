## 1. Что получит пользователь

Пользователь открывает своего официального ИИ-агента, описывает короткий ролик, получает MP4, просит изменения обычными фразами и сохраняет редактируемый проект с исходниками и историей. Подписка или API обеспечивает работу агента; локальная студия создаёт поддерживаемую анимацию, монтирует материалы и кодирует фильм. Сама студия бесплатна; сторонние подписки и API имеют собственные лимиты и оплату.

Объём этой итерации: ролики на 15–30 секунд из 3–4 сцен, оба существующих формата, кириллица, музыка, цвета бренда, восемь типов правок, повторное открытие и переносимая папка проекта. Реалистичная нейросетевая съёмка из одного текста, произвольная анимация, локальная видеомодель и полный набор Higgsfield сюда не входят.

Уже реализованные editor, CLI, scene preview, import, restore, API-runner и offline Replicate flow сохраняются. Их не писать заново. Проверенный ContextOS-фильм служит регрессионным примером, а не новым результатом этой итерации.

## 4. Этап 1 — законченный контракт создания и правок

Работать через `src/project.ts`, schema/types, CLI и существующие adapters. Новые возможности должны быть доступны обычному агенту и API-runner, а не только внутренней функции.

### Обязательные изменения

- **JSON с BOM.** Общий reader для CLI action/request/approval/draft/resolution: поддерживает UTF-8 с/без ведущего BOM; ошибочный JSON даёт `INVALID_JSON`, exit 2 и понятное имя входа без вывода секретного содержимого. Не обещать поддержку всех кодировок PowerShell. Stdin добавлять только при реальной потребности с отдельным явным контрактом.
- **Бренд.** Частичный `brand` patch: theme/background/foreground/accent; неизвестные поля и невалидные цвета отклоняются. Theme-only действие должно иметь документированное предсказуемое поведение: выбрать соответствующую читаемую палитру, если новые цвета не заданы; явные цвета пользователя имеют приоритет. Сохранять font и историю. Полный restore возвращает прежний бренд.
- **Создание.** `new --dir D [--aspect 9:16|16:9] [--title TEXT]`; title задаёт текст первой сцены, а не скрыто меняет project ID. Старые команды без флагов сохраняют поведение. Формат должен задаваться и через API-agent путь существующим `composition` или новыми параметрами адаптера.
- **Атомарная сборка.** `batch` из 1–32 обычных действий, необязательная короткая label, один ETag/lock/commit/snapshot. Назначение — принять логическую сборку целиком; ускорение не считать доказанным по уменьшению числа команд.

### Условия корректности batch

Вложенные batch и restore/restore-scene запрещены. Перед применением каждого действия проверять его форму, разрешённые поля и ID; одна итоговая валидация manifest не заменяет валидацию действий. В общую функцию применения переносить и проверки перед старым switch, а не только его тело. Применять к копии, валидировать конечный проект и commit через действующий API. При ошибке до commit проект, ETag, источники, receipts и history остаются прежними; ответ называет индекс и причину. Не менять существующие правила неопределённого результата commit/receipt в provider flow.

Imports остаются отдельными операциями. Добавление batch не разрешает перезаписывать assets или историю и не превращает файловый импорт в часть транзакции без отдельного дизайна.

### Preview и API-agent

Текущий `scripts/api-agent.mjs` проверяет preview только у верхнего `edit-scene`. Новый batch не должен обходить это условие. Для первой реализации принять простой контракт: когда API-runner требует preview для существующего фильма, отклонять batch с понятной ошибкой и предлагать отдельные preview/edit. Первоначальная сборка нового фильма до первого render может использовать batch в существующем явном initial-creation режиме. Не сбрасывать requirePreview по просьбе модели. Обычные сценовые правки сохраняют привязку exact action + ETag + previewToken.

Не добавлять сложный preview нескольких сцен ради batch. Если он станет необходим, это отдельное обоснованное расширение с теми же гарантиями. Изменение бренда/формата проверяется полным экспортом в новую папку и возможностью restore; не изображать scene-preview как просмотр всего глобального изменения.

**Приёмка:** BOM/brand/new проходят реальные CLI cases; batch создаёт четыре сцены с +1 snapshot после imports. Проверены unknown action/field, вложенность, ошибка в середине, stale ETag, invalid final manifest и API batch rejection при requirePreview. Existing exact-preview regression остаётся зелёной. Неуспешные операции не изменили bytes/history. Обновлены `docs/MANIFEST.md` и reference формата.

## 5. Этап 2 — skill и один каталог действий

1. `references/edits.md`: E1–E8 с валидными примерами, выбором target/revision, preview/export и проверкой результата. Добавить удаление/добавление сцены и громкость музыки, если они уже поддерживаются.
2. Skill: doctor → бриф/storyboard → new → необходимые imports → initial batch → render/просмотр → state → preview/edit либо глобальная операция → export → reopen/restore. Детали вынести в references; границы и разрешения изложить кратко, без повторов.
3. API-runner получает тот же каталог: его список загружаемых файлов сейчас фиксирован, добавить edits.md явно. Уточнить различия между CLI и API initial/edit режимами, лимиты размера actions и понятные ошибки. Не предлагать модели недоступные shell/import операции: API использует заранее разрешённые материалы через свой существующий путь.
4. Проверить установщик на внешней тестовой папке, сохранив существующие skills пользователя. Установка в текущую `.agents` и изменение login не нужны для разработки каталога.
5. Behavioral integration `edit-catalog`: выполнить примеры через CLI на коротких fixtures; считать snapshots с учётом imports; проверить restore глобальных настроек отдельно от restore-scene. Одного общего источника примеров достаточно, тест не должен ограничиваться поиском строк.

**Приёмка:** все E1–E8 выражаются штатными операциями, инструкции соответствуют CLI help и API tools, существующий проект правится без прямой записи JSON, все references входят в runtime.

## 6. Этап 3 — визуальные улучшения по результатам baseline

Выбрать до двух задач, объяснив пользу конкретными кадрами и брифами. Если исходные ролики проходят проверяемые требования, допускается ноль изменений с доказательствами. Приоритет — исправить реальный дефект текста/композиции/ритма; затем расширять выразительность.

Окончательная оценка человеком — отдельный пункт итоговой приёмки.

## 8. Этап 5 — установка и реальные сессии

### Техническая приёмка

1. Выполнить `npm run release:prepare` и `npm run verify:package` последовательно. Подготовка архивов не является публикацией.
2. Создать отдельный consumer через `mkdtemp` вне checkout, с пробелом и кириллицей в имени. Проверить resolved path и `realpath`: он не находится внутри репозитория. `artifacts/v0.2/` подходит для отчёта, но не для этого consumer.
3. Установить tgz, skill и разрешённые fixtures из пакета/проверенного переносимого набора. Выполнить B1–B5 и распределённые правки из §2 только через установленный CLI/skill. Не импортировать исходный `src/`, локальный `dist/` checkout или закрытые проекты.
4. Для каждого брифа сохранить исходный и изменённый MP4, project/assets/history, contact sheet, команды/exit codes, фактический формат/длительность, ошибки, время и соответствие брифу. Для E7/full restore сравнить с правильной исходной версией. Повторно открыть каждый проект.
5. Сохранить переносимый проект и открыть его после копирования в ещё одну папку с исходниками и history. Это проверка на этом компьютере; другой компьютер не считается проверенным.

### Проверка главного обещания

Хотя бы один бриф с двумя последующими правками должен пройти **в свежей официальной модельной сессии выбранного клиента**, из consumer-папки, по skill без чтения исходников. Стартовая сессия получает бриф и материалы, затем отдельными сообщениями — правки, затем reopen. Зафиксировать клиент/версию/режим, фактические tool calls и результаты; discovery без model turn не засчитывается.

Если бюджет или клиент недоступны, закончить техническую часть и оставить эту проверку NOT RUN. Не объявлять всю v0.2 готовой на основании self-run или mock responses. Работать в ранее разрешённом режиме; дополнительный API-бюджет согласовывать только если его действительно нет. Не выводить tokens, account secrets или session URLs.

Codex, Claude Code и прямой API проверяются раздельно. Один прошедший клиент закрывает минимальный пользовательский сценарий; другие остаются явно непроверенными. Для нового API-runner провести offline contract cases в любом случае; реальное соответствие новым brand/batch/edits считать установленным только после разрешённой живой сессии. Сам по себе прежний API-фильм не подтверждает новые действия.

Сценарий B4 для свежей сессии: создание → E2 → E3 → E7. Две исправляющие просьбы могут входить в технический сценарий; если их выбрал агент, так и написать. Для человеческого приёмочного прогона человек выбирает свои две правки и смотрит/слушает полученный фильм. Независимый участник проходит существующий USER_TRIAL_RU; не выдавать self-run за опыт другого человека.

## 9. Проверки, границы и завершение

`AGENTS.md` определяет обязательные проверки. Для обычных изменений — `npm run check`; для project/renderer/server/studio — `npm run test:integration`, последовательно. После группы зависимых правок выполнить проверки один раз; повторять после новых изменений/ошибок. Provider recovery сохраняется: проверить затронутые generation tests, при необходимости `npm run test:generation`, не запускать автоматически live variant. Документация — `npm run check:release`. Новые тестовые файлы включить в явные npm scripts, иначе они не исполнятся.

Источники/история/receipts сохраняются; принятые проекты изменяет project API; preview не записывает draft; общий encoder, timing/crop, v1/v2 и loopback/session/Host/Origin/path checks остаются. При изменении поведения конфликтов проверить настоящий UI. Локальные проекты, `.env`, настройки клиента и исследовательские копии не очищать. Архивные материалы не являются текущими инструкциями.

Не входят: новые media providers, Replicate live, локальные видеомодели, свой chat/OAuth/billing, мультитрек, 4K/HDR, новый UI framework, обновление номера версии и публикация. Эти возможности не нужны для завершения текущего результата.

Итоговый `artifacts/v0.2/ACCEPTANCE.md` содержит:

| Проверка | Что необходимо для статуса «пройдено» |
| --- | --- |
| Реализация и установленный пакет | B1–B5, E1–E8, BOM/brand/batch guards, RU/EN, reopen/restore, source/history и обязательные tests с exit 0 |
| Свежий клиентский сценарий | Реальная новая модельная сессия, бриф, последующие правки и reopen из установленной копии |
| Качество | Технические проверки кадров/звука отдельно; просмотр и прослушивание человеком со списком замечаний, которые мешают использовать ролик |
| Независимый пользователь | Реальный участник по USER_TRIAL_RU; фиксируются помощь и препятствия. Если участника нет — NOT RUN, не блокировать независимую реализацию |
| Дополнительные клиенты/API | По каждому фактический режим и результат, либо NOT RUN с причиной |

Общий `DONE` допустим только после технической приёмки, свежего клиентского сценария и человеческого просмотра/двух правок без оставшихся препятствий для основного сценария. До этого писать прямо: «Реализация проверена; осталось …», перечислив конкретный доступ или человеческое действие. Независимый пользователь/другие ОС — отдельные ограничения распространения, не выдумывать их завершение. Не закрывать обязательный пункт статусом DONE_WITH_CONCERNS.

Передать MP4, переносимые проекты и короткую инструкцию продолжения. Разницу до/после подтвердить измерениями, не числом новых файлов. Дальнейшее расширение выбирать по наблюдениям пользователей и измеренным задержкам; новый большой план автоматически не писать.
