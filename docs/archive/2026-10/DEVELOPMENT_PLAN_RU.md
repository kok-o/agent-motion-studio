## 1. Цель и смысл продукта

### 1.1. Продукт, к которому идём

**Agent Motion Studio — бесплатная открытая локальная студия, в которой человек создаёт и правит видео через своего агента по подписке или API.** Пользователь приносит задание и разрешённые материалы. Агент составляет сцены, управляет анимацией и монтажом через инструменты студии, проверяет результат и выполняет правки. Студия сохраняет проект, источники и принятые дубли и локально рендерит фильм.

Источниками AI могут быть:

- официальный агент пользователя по подписке, который вызывает инструменты студии;
- облачные модели через API-ключи пользователя;
- официальные OAuth/MCP-интеграции, если конкретный сервис разрешает такой способ использования;
- локальные модели на поддерживаемом оборудовании — отдельный режим следующего этапа.

За саму студию, её локальные функции монтажа и экспорт не требуется подписка разработчика проекта. Облачные модели расходуют деньги или лимиты пользователя у выбранного сервиса. Открытый код студии не делает сторонние вычисления бесплатными.

Пользователь владеет локальной копией проекта, исходниками, принятыми дублями и историей. Для облачной генерации необходимые prompt/reference передаются выбранному сервису. Формулировка «локальная студия» не должна обещать, что облачные запросы остаются на устройстве.

### 1.2. Первый пользователь и задача

Первый сценарий — короткий рекламный или объясняющий ролик для самостоятельного автора: продукт, устройство, игровой предмет или художественный объект. У пользователя есть задание, свой агент по подписке либо API и при необходимости изображение/клип объекта. Поддерживаемый motion и монтаж своих материалов должны работать без отдельного ключа видеогенератора. Реалистичные нейросетевые сцены остаются дополнительным режимом того же проекта.

Целевой результат:

1. Создать фильм на 15–30 секунд из 3–4 сцен.
2. Посмотреть отдельные сцены и целый фильм.
3. Попросить изменить вторую сцену.
4. Получить новый дубль без потери удачных остальных сцен.
5. Сравнить результат и явно принять его.
6. Экспортировать MP4.
7. При необходимости вернуть предыдущий дубль.
8. Открыть проект позже или передать редактируемую копию другому человеку.

Это гипотеза полезного сценария. Подтверждение спроса, художественного качества и удобства требует независимого использования.

### 1.3. Почему пользователь выберет проект

Проверяемое обещание: **«Сделай короткий фильм со своим AI. Меняй любую сцену, сохраняя удачные дубли и весь проект».**

Преимущество нужно доказывать:

- меньшим количеством повторных генераций при правке одного кадра;
- сохранностью принятой работы;
- простотой повторного открытия, восстановления и передачи проекта;
- понятным контролем расходов;
- доступностью для внешнего агента через тот же контракт, которым пользуется UI.

Количество подключённых моделей, строк кода, шаблонов или зелёных тестов не заменяет эти результаты.

### 1.4. Три независимых слоя

| Слой | Что делает | Где выполняется |
| --- | --- | --- |
| Агент | Понимает задание, создаёт описания сцен, выбирает и настраивает анимацию, управляет монтажом, проверяет кадры и делает правки | Официальный клиент с подпиской пользователя либо поддержанный API-доступ |
| Локальная студия | Исполняет поддержанные сцены и анимацию, собирает графику/клипы/звук, хранит проект и историю, рендерит MP4 | Компьютер пользователя |
| Дополнительные AI-материалы | Создаёт нейросетевые изображения, клипы или звук, когда они нужны | Разрешённая подписочная интеграция, отдельный media API или поддержанная локальная модель |

Локальный монтаж, ограниченные процедурные сцены и экспорт уже существуют. Фильм из задания и демонстрационные итерации через Codex подтверждены; следующая работа проверяет оставшиеся клиенты и удобство нового пользователя. Агент может создавать описание анимации, а кадры исполняет локальный renderer; произвольный код из импортированного проекта не выполняется автоматически. Coding-подписка сама по себе не даёт модель реалистичного движения. Оптимизация FFmpeg ускоряет местную обработку, а не удалённую модель.

### 1.5. A1: выполненный сценарий и оставшиеся клиентские проверки

Список ниже сохраняет исходный acceptance contract, а не поручение переделать демонстрацию. Создание фильма, две выбранные агентом правки, restore/reopen и API-agent закрыты в границах [матрицы](../../AGENT_VALIDATION.md). Они не заменяют две новые человеческие просьбы или поддержку всех клиентов. Открыты новая Codex модельная сессия, Claude Code, независимый человек и непрерывный просмотр/звук. Перед продолжением прочитайте локальный `artifacts/contextos-ad/RESULT_RU.md` и связанные результаты, если доступны; публичному получателю достаточно матрицы и выданного переносимого проекта.

Пользователь в своём официальном Claude Code или Codex задаёт: «Сделай рекламный ролик на 20 секунд из этих материалов; затем измени вторую сцену и сократи финальный титр». Студия должна дать фильм, редактируемый проект и понятную возможность восстановить предыдущий вариант.

Работы A1:

1. Проверить существующие `new/init`, `state`, `import`, `edit`, `validate`, `render`, историю и draft preview; использовать их общий контракт. Обычные accepted edits не писать напрямую в JSON.
2. Подготовить установку/обнаружение skill для официальных Claude Code и Codex, с переносимыми путями и коротким пользовательским запуском. Проверить документацию текущих клиентов; не считать наличие `skills/` автоматическим доказательством обнаружения skill.
3. Дать агенту понятную структуру brief/shot plan: цель, формат, длительность, 3–4 сцены, доступные материалы, текст, темп, цвета и разрешённые способы получения новых материалов. Использовать supported scene types, а необходимые расширения делать узко.
4. Завершить local-only сценарий: новый brief → проект → сцены → preview/export → визуальная проверка → две пользовательские правки → экспорт → restore/reopen. Новый video API account не нужен; обычные model limits подписочного агента продолжают действовать.
5. Проверить оба названных клиента отдельно. Сохранить фактические команды/tools и результаты настоящих сессий, без credential/session dumps. Если один клиент недоступен, маркировать его NOT RUN; тест сервиса не доказывает работу клиента.
6. Предусмотреть тот же путь через собственный API-ключ модели агента: официальный клиент с поддерживаемой API-конфигурацией либо минимальный adapter к тому же tool contract. Выбрать один доступный путь, описать его биллинг, проверить локальный контракт; реальные API-вызовы только в уже разрешённом бюджете. Не путать agent API key с video API key.
7. Проверить MP4/decode и сохранность проекта, а также посмотреть реальный contact sheet/кадры и непрерывное воспроизведение доступным способом. Читаемость текста, композиция и темп имеют отдельный visual acceptance; технический pass не заменяет его.
8. Передать человеку без внутреннего контекста инструкцию запуска и повторить его собственный brief. Зафиксировать вмешательства разработчика и ограничения вместо заявления «работает со всеми агентами».

Минимальная матрица: обнаружение skill; фильм из нового brief; две локальные правки; external-edit conflict; restart/reopen; restore; отсутствие обращений к media provider при local-only запросе; отдельный статус Claude Code, Codex и API-agent. Когда API/подписочный доступ недоступен, закончить независимую реализацию, инструкции и тесты; не выдумывать сессии и не требовать ключ Replicate для этой вехи.

Первый агентный сценарий можно выполнить без встроенного чата: пользователь работает в своём клиенте, а UI студии служит просмотром и редактором того же проекта. Встраивание чата и дополнительных клиентов следует после доказанного workflow.

Для реалистичных AI-клипов сохранить три возможных входа: готовый разрешённый файл, официальный доступ к генератору через подписку/MCP при наличии такого контракта, media API. Ручное получение и импорт клипа из внешнего сервиса нужно обозначать как ручной этап; не выдавать его за автоматическую подписочную интеграцию. Локальную видеомодель оценивать отдельно по лицензии и оборудованию.

Ориентиры: [Claude Code skills](https://code.claude.com/docs/en/skills), [Claude Code access terms](https://code.claude.com/docs/en/legal-and-compliance), [Codex skills](https://learn.chatgpt.com/docs/build-skills), [Sign in with ChatGPT limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations). Авторизация остаётся в официальном клиенте; общий UI сбора подписочных токенов не требуется.

## 2. Текущее состояние и отправная точка

### 2.1. Стадия

Версия 0.1.0 — экспериментальный developer preview локального редактора. Это работающий технический прототип перед первым законченным генеративным MVP.

Уже реализовано:

- Node.js/TypeScript CLI и сервер на loopback;
- браузерный UI на HTML/CSS/JavaScript;
- импорт video/image/audio с копированием и хешами;
- общий JSON-проект для UI и CLI;
- v1/v2 validation и совместимость;
- storyboard, trim, cover/contain, focal point;
- несохранённый scene preview через общий с экспортом encoder;
- история и восстановление отдельной сцены;
- конфликты между UI и внешним агентом;
- титры, изображения, музыка и ограниченные narration/captions;
- экспорт H.264/AAC MP4 и проверка полного декодирования;
- подготовка source/runtime архивов и переносимого примера;
- agent skill и инструкции для клиентов.

Не реализовано:

- video-generation provider;
- сохранённые генерационные задания;
- библиотека сгенерированных кандидатов с Accept/Reject;
- встроенный чат или собственный автономный режиссёр;
- локальный inference видеомодели;
- кэш по сценам;
- простой установщик всех системных зависимостей;
- полноценный multitrack timeline.

### 2.4. Ограничения, которые нельзя пропустить

1. `patchScene` сохраняет `scene.id` и `scene.type`. В первой генеративной версии поддерживать **video → video** для существующей сцены. Превращение титра/картинки в video — отдельная операция следующего этапа.
2. `importMedia` уже делает commit и меняет assets/history/ETag. Его нельзя вызвать для просмотра кандидата и утверждать, что проект не изменился.
3. Текущий `previewScene` ожидает asset, уже присутствующий в manifest. Для candidate preview нужен временный manifest либо общий внутренний builder с дополнительным проверенным asset.
4. Некоторые действия UI автоматически сохраняют dirty form. Выбор кандидата не должен записывать его в обычное поле сцены до отдельного Accept.
5. Registry ограничен 24 assets; история — 100 ревизиями; сцены — 12; фильм — 60 секундами. Первую версию не строить на бесконечном числе принятых дублей.
6. Смена импорта меняет ETag, а UI сравнивает его с экспортом. Staging кандидатов вне manifest позволяет избежать ложного устаревания принятого фильма.
7. `scripts/build.mjs` собирает TypeScript-файлы верхнего уровня `src/`. Если создать `src/generation/`, сборку и package paths придётся осознанно расширить. Для небольшой первой реализации допустимы несколько файлов верхнего уровня.
8. Текущий runtime cancellation общий для процесса. Отмена HTTP polling одного job не должна вызывать глобальный `cancelProcesses()` и ломать дальнейшую работу сервера.
9. History содержит ссылки на старые assets. Проверять целостность и переносимость нужно для текущих сцен и сохранённой истории.
10. Текущий agent skill и часть его references ориентированы на ранние motion/v1-сценарии. Их нельзя считать готовой документацией generative v2 editing.

Работать в подходящем текущем checkout или изолированной рабочей копии согласно среде. При создании ветки использовать принятый в текущем окружении префикс; для этого проекта по умолчанию `koko/`. Не создавать публичные issues/PR/comments без задачи на внешнюю публикацию.

- режима, длительности и разрешения;
- суммы/лимита и максимального числа submit;
- конкретного reference, разрешённого к отправке;
- назначения результата: локальная проверка либо разрешённая публикация.

Наличие ключа в окружении не означает разрешения тратить деньги или отправлять файлы. Подтверждение, уже данное на этот же сценарий и бюджет, сохраняется: повторно спрашивать перед каждым poll/download не нужно.

Если данных нет, агент выполняет весь независимый локальный объём: рабочий adapter по официальному контракту, UI, CLI, tests, документацию и подготовленный запрос. Затем указывает, какие конкретно данные нужны для финального live-run. Не выдавать эту границу за невозможность написать код.

### 3.4. Как принимать технические решения

- Сначала использовать существующие API и установленный стек.
- Выбирать минимальную поддерживаемую реализацию для одного провайдера.
- Не добавлять БД, брокер очередей, UI framework, generic plugin platform или собственный auth server ради первой сцены.
- JSON-state и один local runner достаточны, если проверены взаимное исключение и восстановление.
- Решение, влияющее на форматы, безопасность, бюджет или переносимость, записать коротко: проблема → выбранный вариант → причина → ограничения.
- Пользовательские цели важнее механического соблюдения предложенных имён файлов. Агент может изменить структуру с объяснением и проверкой.

## 5. P0: подготовка и выбор первого подключения

### 5.1. Baseline

Из корня репозитория:

```powershell
git status --short
git log -1 --oneline
npm run check
node dist/cli.js doctor --json
npm run test:integration
```

Если dependencies отсутствуют, перед сборкой установить через `npm ci --ignore-scripts`. Не переустанавливать всё без причины. Media tests выполняются одним процессом последовательно; параллельные проверки других агентов не должны запускать Chrome/FFmpeg.

Сохранить команды, exit codes, время, commit и версии инструментов в локальные `artifacts/<run-id>/`. Не включать credentials, session URLs и private account identifiers в публичные отчёты.

Предсуществующие failures записать отдельно. Не отключать их и не присваивать исходные зелёные результаты новому checkout.

### 5.2. Зафиксировать продуктовую формулировку

При начале реализации согласовать README/roadmap с разделом 1 этого плана:

- бесплатная студия и локальный экспорт;
- сторонние AI-расходы принадлежат выбранному пользователем сервису;
- внешний агент — достаточная первая интеграция;
- локальная генерация возможна отдельным этапом;
- ближайшая основная цель — фильм из задания через агентную подписку/API; generated replacement shot — отдельный media workflow.

Разделять Current и Planned. Не писать «supports provider X» до реально реализованного adapter; отдельно маркировать «offline contract verified» и «live verified».

### 5.3. Выбор провайдера

Не угадывать provider по имени Higgsfield. Приоритет — официальный и проверяемый доступ пользователя, поддержка нужного reference/длительности, понятные расходы и восстановление известного job.

Порядок решения:

1. Если пользователь уже указал сервис/ключ/бюджет, проверить его актуальные возможности.
2. Если сервиса нет, сравнить небольшое число официальных API и выбрать один по таблице ниже. Само исследование и выбор adapter не требуют платного запроса.
3. Если модель не может покрыть нужную длительность сцены или легально принять reference, выбрать другую модель/провайдера до реализации adapter.
4. Зафиксировать конкретный provider, model ID, revision/version при наличии и один режим. Не строить общий marketplace.

| Критерий | Что выяснить | Причина |
| --- | --- | --- |
| Официальный доступ | API key/OAuth/MCP; допустимость нашего клиентского сценария | Подписочные credentials не универсальны |
| Режим | T2V или I2V; допустимые references | Для предметного тизера I2V предпочтителен, если доступен |
| Время | Допустимые durations, минимальный платный clip, fps | Покрыть интервал сцены без незаметного изменения монтажа |
| Геометрия | Resolution, aspect ratios, размер и формат результата | Совместимость с текущим pipeline |
| Reference upload | Официальный file endpoint, inline data или иной документированный способ | Не создавать публичный storage и tunnel ради демо |
| Асинхронность | Submit, status, result, expiry, cancel | Возможность resume известного задания |
| Идемпотентность | Request key, lookup by client ID, срок действия | Поведение после потери ответа submit |
| Биллинг | Валюта/credits, audio/resolution multipliers, failed/cancelled requests | Достоверная оценка и ограничение расходов |
| Результаты | Retention, signed URLs, повторное получение результата | Не перегенерировать при истечении download URL |
| Ограничения | Rate limits, concurrency, max payload, account availability | Предсказуемые ошибки и backoff |
| Права | Использование inputs/outputs, модельная лицензия | Переносимость и возможность распространять демо |

Создать, например, `docs/GENERATION_PROVIDER_DECISION.md`. Записать ссылки на первичные документы, дату проверки, выбранный путь и отклонённые альтернативы в нескольких предложениях. Цены хранить вместе с датой/источником; не переносить старую цену в код как бессрочную истину.

Decision record должен содержать точный endpoint ID, snapshot/hash его input schema, допустимые output bounds, способ загрузки reference, срок хранения inputs/outputs, доступность файлов по URL и нерешённые ограничения. Не приравнивать длительность сцены к оплачиваемым единицам модели: сервис может тарифицировать фиксированный клип, число кадров или другое значение. Если фиксированного максимума стоимости нет, это явно показать до запроса разрешения; локальный timeout не гарантирует прекращение расходов.

Для первичного сравнения достаточно двух-трёх официальных вариантов, например [Replicate Wan I2V](https://replicate.com/wan-video/wan-2.2-i2v-fast/api/schema), [fal Wan I2V](https://fal.ai/models/fal-ai/wan/v2.2-5b/image-to-video/api) и упомянутого ниже Veo. Это кандидаты для исследования, а не заранее выбранные или уже поддерживаемые интеграции. Перепроверить актуальные API schema, условия и цену. Если применимость условий провайдера к нашему приложению неоднозначна, записать вопрос и выбрать приемлемый вариант до live-run; не заявлять совместимость по одному наличию API. Для fal отдельно сопоставить [общие условия](https://fal.ai/legal/terms-of-service) и [API terms](https://fal.ai/legal/api-services).

Среди вариантов, прошедших обязательные критерии, выбрать минимальную максимальную стоимость разрешённого запроса, затем меньшую сложность интеграции. Если endpoint не подходит, сменить решение до реализации второго adapter. Во время выполнения запроса автоматического перехода на другую модель или платного fallback нет.

### 5.4. Подписки и границы первого этапа

Для ветки video API использовать **свой API-ключ видеопровайдера**, если пользователь выбрал этот способ получения новых клипов. Это не требование A1. Агент по подписке подключается снаружи через CLI/skill; агент с API-доступом управляет теми же инструментами. Встроенный OAuth/чат можно делать отдельной задачей при необходимости.

Текущие первичные ориентиры, перепроверенные при подготовке плана:

- [Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance): пользовательский официальный CLI и собственный API — разные допустимые пути; сбор/проксирование Claude.ai tokens приложением не разрешён. Встраивание неизменённого CLI имеет свои условия.
- [OpenAI Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source) и [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations): официальный маршрут для подходящих приложений имеет отдельные возможности и ограничения; не переносить весь набор ChatGPT tools в студию по предположению.
- [Higgsfield API](https://higgsfield.ai/blog/higgsfield-api): API и MCP используют разные платёжные пути; API имеет отдельный баланс, MCP использует кредиты аккаунта.
- [Veo API](https://ai.google.dev/gemini-api/docs/veo): пример официального асинхронного видеогенератора; возможности и тариф проверять для конкретной модели перед выбором.

Внедрять одновременно Claude OAuth, OpenAI OAuth, Higgsfield MCP и несколько video APIs в P1 не требуется.

## 6. P1: точный пользовательский сценарий

### 6.1. Контрольный проект

Создать личную копию `coffee-ritual` либо другого разрешённого примера. Не менять общий template и пользовательские текущие проекты.

```powershell
node dist/cli.js init coffee-ritual --dir projects/generation-validation
node dist/cli.js studio projects/generation-validation/project.json
```

Для первого replacement выбрать существующую video scene. В coffee example вторая сцена длится семь секунд; перепроверить actual manifest, а не полагаться на это число при другом checkout.

### 6.2. До генерации

В сцене есть действие «Создать новый дубль». Панель показывает:

- текущую сцену, её длительность и принятый исходник;
- prompt и reference, если режим его поддерживает;
- provider/model/mode;
- длительность оплачиваемого клипа и используемую длительность сцены;
- разрешение/aspect ratio, поддержку звука;
- данные, которые будут отправлены сервису;
- оценку стоимости, её источник и степень определённости;
- понятную причину недоступности, если key/model/reference не готовы.

Предпросмотр цены и локальная проверка параметров не отправляют reference и не запускают генерацию. После изменения параметров ранее показанная оценка/подтверждение не должны автоматически применяться к другому запросу.

Для первой версии один submit за одно явное действие пользователя; автоматических повторных генераций нет. Обычный reload, повторное нажатие и polling не создают второй paid job.

### 6.3. Во время генерации

Интерфейс показывает понятное состояние и оставляет доступ к принятому проекту:

- подготовлено;
- отправляется;
- в очереди;
- генерируется;
- ожидает восстановления соединения/авторизации;
- готово к загрузке;
- загружается и проверяется;
- кандидат готов;
- отказ/неопределённый исход отправки.

Не показывать выдуманный процент, если провайдер даёт только статус. Не блокировать проект на весь удалённый job. Пользователь может смотреть старые материалы и вносить другие правки; изменение целевой сцены учитывается при принятии.

Закрытие UI не означает отмены уже оплаченной генерации. «Остановить отслеживание» и «Отменить у провайдера» — разные действия. Второе доступно только при подтверждённой поддержке и не обещает возврат денег.

### 6.4. Получение и просмотр кандидата

Новый клип хранится отдельно от принятого manifest. Панель предлагает исходный candidate playback и точный preview его применения в сцене.

По умолчанию:

- `durationFrames` сцены сохраняется;
- trim нового источника начинается с 0;
- fit/focal берутся из текущей сцены и видны пользователю;
- предыдущий source trim не переносится скрыто на новый клип;
- короткий клип не зацикливается, не растягивается и не дополняется frozen frames автоматически;
- sound policy соответствует текущему ядру: source-video audio не включается незаметно.

Если пользователь меняет candidate trim/crop, эти поля принадлежат candidate draft. Они не записываются в обычный dirty scene form и не принимаются при переключении сцены.

Preview не записывает `project.json`, не увеличивает историю, не меняет assets registry и не помечает старый export устаревшим.

У preview есть fingerprint: candidate hash, целевая сцена/контекст и выбранные duration/trim/fit/focal. После изменения candidate draft прежний preview помечается устаревшим, а Accept требует нового точного просмотра этих параметров. Это проверяется и на сервере: один старый project ETag не обнаруживает изменение candidate crop. Состояние проверки хранится вне accepted manifest.

### 6.5. Принятие и отклонение

Кнопка «Принять дубль» выполняет одну принятую операцию проекта: регистрирует новый immutable asset и меняет ссылку/параметры целевой video scene. Предыдущая сцена целиком сохраняется в истории.

Если во время генерации изменились целевая сцена или существенные параметры композиции, показать сравнение и потребовать осознанного разрешения. Не применять старый candidate поверх более новой правки автоматически.

Reject означает, что дубль не используется в фильме. Первая версия может оставить его локальный файл для повторного просмотра; явное удаление кандидата — отдельное действие. Ни reject, ни cleanup candidates не удаляют принятые assets или файлы, на которые ссылается история.

### 6.6. Экспорт и восстановление

После Accept новый export использует обычный pipeline. Restore возвращает прежние asset, trim, duration, fit/focal и прочие поля сцены. При неизменном окружении остальные сцены и восстановленный фильм должны пройти сравнение декодированных кадров.

Действие «Вернуть предыдущий дубль» должно быть привязано к истории принятой сцены, а не к случайному последнему job. Candidate list и project history — разные сущности.

## 7. Архитектура генеративной части

### 7.1. Минимальная структура

Предлагаемые новые модули; имена не являются обязательным API:

| Модуль | Ответственность |
| --- | --- |
| `src/generation.ts` | Use cases: prepare, submit, reconcile, download, accept/reject |
| `src/generation-store.ts` | Versioned job state, atomic writes, local ownership/locks |
| `src/generation-provider.ts` | Контракт adapter и один production provider |
| `src/generation-media.ts` | Ограниченная загрузка, validation и staging кандидата |
| `src/project.ts` | Shared immutable import helper и atomic accept operation |
| `src/preview.ts` | Candidate draft → общий scene encoder |
| `src/server.ts`, `src/cli.ts` | Два интерфейса к одному generation service |
| `studio/` | Generation panel, job status, candidate preview и acceptance |

Не создавать все файлы заранее ради структуры. Объединять маленькие части, если это сохраняет читаемость. Не помещать весь lifecycle в HTTP route handler.

### 7.2. Хранение

Предлагаемая layout внутри пользовательского проекта:

```text
project.json                  принятый portable manifest
assets/                       immutable принятые источники
.studio/
  generation/
    jobs/<local-id>.json       локальная история generation job
    candidates/<sha256>.mp4    проверенные, ещё не принятые клипы
    staging/                  незавершённые downloads
    runner.lock               владение обработчиком
exports/                      существующие экспорты
```

Credentials размещаются вне проекта. Конкретный storage path выбирается по ОС; для P1 достаточно environment variable или существующего безопасного server-side credential source. Browser получает только configured/not configured и безопасные сведения provider profile.

`.studio` содержит локальное состояние, которое может включать prompts/reference metadata. Его нельзя случайно включать в runtime/source package или public demo. Дополнить ignore и distribution audit для выбранного имени каталога; Git ignore сам по себе не является единственной защитой упаковки.

При открытии скопированного проекта не запускать автоматически remote submissions, polling, uploads или downloads. Скопированный job может принадлежать другому аккаунту. Offline просмотр принятого фильма должен работать без старого аккаунта и без `.studio`.

### 7.3. Что записывать в job

Поля являются проектным предложением, не существующим schema:

| Группа | Минимальные данные |
| --- | --- |
| Идентичность | `schemaVersion`, случайный local job ID, created/updated timestamps |
| Цель | scene ID, исходная revision, ETag, snapshot/hash целевой сцены и важных параметров композиции |
| Запрос | provider/model/mode, prompt, seed если поддерживается, duration/resolution/aspect, прочие разрешённые параметры |
| References | локальные IDs/relative paths, hashes, типы, что реально отправляется |
| Авторизация | имя credential profile/account scope без секрета; fingerprint согласованного запроса |
| Расходы | estimate, currency/credits, источник/дата, approved bounds и число попыток; actual cost только если получен достоверно |
| Submit | client request key, попытка, состояние, remote job ID после получения |
| Наблюдение | последний provider status, poll time, retry/backoff state, нормализованная ошибка |
| Результат | local candidate path/hash/bytes, probe/decode сведения, source duration/fps |
| Решение | pending/accepted/rejected, accept operation ID, принятое scene snapshot/revision при наличии |

Публичное представление job не равно private persisted JSON. Оно исключает secret headers, signed URLs, raw provider bodies и чувствительные account IDs. Provider response — недоверенные данные.

Prompt сохраняется для истории; повторная генерация с теми же полями не обещает идентичных пикселей. Даже seed может не обеспечивать воспроизводимость у конкретного сервиса.

### 7.4. Контракт adapter

Для одного production provider достаточно операций:

- описать capabilities/ограничения;
- проверить и нормализовать локальный request;
- рассчитать estimate, если документировано;
- загрузить reference официальным методом после разрешения;
- отправить generation request;
- получить status известного remote ID;
- получить свежий result locator;
- cancel, только если доступен;
- reconcile неопределённого submit, только если есть документированная возможность.

Provider-specific статусы, field names и errors преобразуются внутри adapter. UI не должен зависеть от структуры raw JSON выбранного сервиса.

Не вводить абстракцию «любой AI-provider» для text, image, video, audio одновременно. Если метод не поддерживается, capability явно false; заглушка не должна возвращать фиктивный успех.

Production backend при отсутствии ключа возвращает понятную ошибку. Fake provider существует в test fixtures/инъекции транспорта и не включается автоматически для пользователя.

## 8. Состояния, перезапуск и контроль повторов

### 8.1. Семантика состояний

Имена разрешено адаптировать; следующие различия обязательны:

| Состояние | Значение | Что можно делать автоматически |
| --- | --- | --- |
| `prepared` | Запрос проверен локально, ещё не отправлялся | Ничего платного |
| `uploading` / `uploaded` | Разрешённый reference передаётся или уже загружен | Сохранять upload ID/expiry; не запускать generation без её разрешения |
| `submitting` | Intent записан, отправка могла начаться | После аварии перейти к проверке неопределённости |
| `submission_unknown` | Ответ потерян, удалённое принятие неизвестно | Только безопасный lookup при поддержке; не blind POST |
| `queued` / `running` | Remote ID сохранён | Ограниченный polling этого ID |
| `output_ready` | Удалённый результат готов | Получить result metadata/download согласно исходному разрешению |
| `downloading` | Идёт загрузка во временный файл | При restart безопасно повторить download, не generation |
| `ready` | Candidate прошёл проверку | Показать preview; не принимать автоматически |
| `failed` | Установлен окончательный отказ конкретной стадии | Предложить действие, различая retry download и новую генерацию |
| `cancelled` | Провайдер подтвердил отмену либо запрос отменён до submit | Не утверждать refund без сведений |

Отдельно хранить pause reason для auth/network/poll timeout и решение по candidate. Разрыв соединения не означает окончательный provider failure. `accepted/rejected` не должны стирать историю удалённого выполнения. Результат `completed` проверяется на ошибки и наличие media согласно контракту сервиса; само слово в status не гарантирует успешное видео. Истёкший и окончательно удалённый результат — отдельная диагностируемая причина, без повторной генерации.

### 8.2. До и после submit

1. Сохранить job и точный request fingerprint до сетевого запроса, включая reference upload.
2. Проверить, что параметры и reference hashes соответствуют подтверждённому запросу; при I2V загрузить только согласованный reference официальным способом и сохранить upload metadata. Не отправлять весь проект или исходное видео вместо выбранного изображения.
3. Под job lock записать intent `submitting`.
4. Отправить один запрос с idempotency key, только если провайдер документирует его поддержку. Иначе не выдумывать такое свойство API: один POST и консервативный `submission_unknown` при потере ответа.
5. Сразу сохранить remote ID до длительных следующих операций.
6. Перейти к отслеживанию.

При restart в `submitting` без remote ID исход неопределён. Если provider поддерживает поиск по ключу, выполнить его. Если нет, показать инструкции сверки в сервисе. Новая генерация требует отдельного осознанного запуска, поскольку предыдущая могла быть оплачена.

Не называть это гарантией exactly-once внешнего сервиса. Гарантия приложения — отсутствие слепого повторного submit и сохранение известной неопределённости.

### 8.3. Повторные клики и несколько процессов

- Один client intent ID соответствует одному local job; повторный HTTP/CLI запрос возвращает тот же job.
- Тот же client intent ID с другим canonical request hash отклоняется; он не заменяет параметры старого job и не создаёт скрытую новую генерацию.
- Ключ повторного запуска должен переживать перезагрузку клиента, а не создаваться заново на каждый клик.
- Серверные проверки обязательны даже при disabled UI button.
- Для P1 разрешён один активный generation submit/runner на проект. Остальные запросы получают понятное busy либо попадают в локальную очередь без автоматического paid submit.
- HTTP, CLI и второй процесс должны пользоваться одним persisted state и правилом владения.
- Не удерживать project edit lock во время сети, очереди или скачивания.
- Для операций, которым нужны оба lock, порядок один: job → project. Обратного порядка и вложенного вызова публичного API с повторным project lock быть не должно.

### 8.4. Polling и отмена

Параметры polling следуют документации провайдера, учитывают `Retry-After`, backoff и предел числа/частоты запросов. Не опрашивать бессрочно каждые миллисекунды.

401/403, временные 5xx, 429 и недоступная сеть должны иметь различимые действия. Тайм-аут локального ожидания ставит наблюдение на паузу; удалённая генерация могла продолжиться.

Локальный AbortController останавливает конкретные HTTP операции. Выход студии завершает принадлежащие ей процессы и записи состояния; он не отменяет удалённый job без поддерживаемого и запрошенного cancel.

Установить отдельный конечный deadline и число retries для upload, poll и download. Generic retry middleware не повторяет generation POST. Если у провайдера есть собственные retries/fallback, задать и описать их явно по официальному контракту; обещание «один submit» само по себе не описывает внутреннюю политику сервиса.

### 8.5. Crash recovery

Для versioned JSON-store использовать запись временного файла и atomic rename в пределах одного каталога. Проверять schema до использования. Corrupt state не должен обнуляться и повторно создавать генерацию.

Различать:

- обычный restart UI/server;
- аварийное завершение процесса в контрольной точке;
- полное отключение питания/потерю диска — это отдельная, не обещанная без проверки durability.

Stale lock recovery должна проверять владение/состояние; не удалять все lock files при запуске. Если корректное восстановление не определено, дать безопасную диагностику и сохранить данные. Наличие PID само по себе недостаточно из-за переиспользования PID и копирования проекта.

## 9. Candidate storage, preview и принятие

### 9.1. Скачать и проверить

Download service получает locator от adapter для известного job. Не предоставлять общий endpoint «скачай любой URL».

Обязательное поведение:

1. Проверить разрешённый origin/transport и redirect policy.
2. Не отправлять provider Authorization header на чужой CDN автоматически.
3. Загружать потоком в staging с лимитом bytes, timeout и отменой.
4. Проверять реальное количество bytes независимо от `Content-Length`.
5. Проверить container, streams, duration, geometry, fps и полное декодирование в пределах поддерживаемого контракта.
6. Посчитать SHA-256 локального результата.
7. Атомарно перенести проверенный candidate в content-addressed staging storage.
8. Только после этого показать `ready`.

Для P1 предпочтителен provider output в поддерживаемом MP4. Если нужен normalization, хранить original candidate и derivative отдельно, со связью и hashes; не переписывать original bytes. Поддержка иных форматов не является обязательной целью первой версии.

Различать проверку source и final export: существующий final verifier может требовать H.264/yuv420p, тогда как допустимый MP4-источник имеет иной декодируемый codec. Строить candidate validation на source probe и строгом полном decode с ограничениями размера/длительности, а не механически применять все требования финального файла. Сохранить оригинальный audio stream в source, но явно сообщить, что текущий scene encoder его не включает в фильм; не оплачивать дополнительную генерацию звука по умолчанию.

Истёкший URL требует свежего locator для прежнего job. Повреждённый/обрезанный download можно скачать повторно; это не разрешение заново отправлять prompt на генерацию.

### 9.2. Preview без изменения проекта

Добавить внутреннюю операцию candidate preview, которая:

- читает текущий validated manifest и ETag;
- получает candidate по local job/candidate ID, а не по произвольному пути из browser;
- проверяет hash и bounds candidate;
- создаёт временный manifest внутри project root, сохраняя все сцены и контекст их timing;
- добавляет в эту копию candidate asset с относительным безопасным path;
- применяет draft patch только к целевой video scene;
- сохраняет контекст сцены и global timing, чтобы preview совпадал с export;
- вызывает существующий `loadManifest`/общую validation и `encodeScene`;
- проверяет output и неизменность источников;
- удаляет temporary manifest и только свои временные файлы;
- возвращает preview metadata, исходный ETag и отметку устаревания.

Результат содержит `previewId` и fingerprint нормализованного candidate draft и render-контекста. Generation service сохраняет соответствующее безопасное metadata в sidecar. Accept сверяет его с текущим intent; клиент не может подтвердить другой trim/crop одним полем «preview готов». Самый простой P1 может включать весь исходный ETag в fingerprint и требовать refresh после любой принятой правки.

Предпочтительно вынести общий внутренний helper из `previewScene`, сохранив существующее поведение. Не копировать FFmpeg filter logic в generation module.

Перед построением временного preview полностью проверить принятый проект, включая его history и ссылки. После этого временный render-only manifest может не содержать history, operation receipts и assets, не используемых его сценами, audio и прочими render-полями. Это отдельная временная композиция, а не изменение принятого проекта или способ скрыть его невалидность. Candidate получает собственный ID; нельзя подменять bytes под ID принятого asset, на который ссылаются другие сцены. Большие исходники на каждый preview не копируются.

Предел accepted registry остаётся 24. Даже если временный preview успешен после исключения неиспользуемых assets, Accept при заполненном registry должен явно отказать до commit. Если минимальная временная композиция тоже превышает schema cap, exact preview недоступен с понятной причиной; raw playback остаётся доступным. Отдельно проверить проект с 24 принятыми assets, в том числе несколько сцен с общим источником.

Сохранить текущие ограничения exact scene preview для narration/captions и сообщать о них до paid submit. Расширение поддержки overlays — отдельная задача; нельзя возвращать приблизительный ролик под видом точного preview.

### 9.3. Одна принятая транзакция

Добавить в `src/project.ts` операцию наподобие `acceptGeneratedTake`. Она работает через существующие validation, snapshot и commit.

Под canonical project lock:

1. Перечитать актуальный manifest; сначала распознать уже выполненный operation ID по правилам ниже, затем проверить ожидаемую версию для новой операции.
2. Проверить существование и type целевой сцены.
3. Проверить fingerprint той версии сцены/композиции, которую пользователь видел при подтверждении.
4. Проверить готовность candidate, hash и параметры выбранного интервала.
5. Проверить asset cap, длину manifest и сохранность необходимых источников.
6. Скопировать candidate в обычный `assets/` content-addressed path, сохранив original candidate.
7. Добавить registry entry и применить patch в одном `next` manifest.
8. Записать один snapshot предыдущей принятой сцены/монтажа.
9. Выполнить общий commit один раз.
10. Вернуть новую revision и receipt принятия.

Для этого разрешён небольшой refactor общего import helper. Не вызывать вложенно два публичных API, каждый из которых получает тот же project lock. Не делать последовательность `importMedia` → отдельный `editProject`, если обещан один атомарный Accept.

После точки успешного commit и при неопределённом исходе promotion запрещено удалять новый asset из общего `catch`: manifest rename мог уже завершиться, а последующий read/ack — упасть. Безопасный orphan source при незавершённой операции предпочтительнее отсутствующего файла принятой сцены. Автоматическая уборка требует отдельной доказанной проверки ссылок.

### 9.4. Идемпотентность Accept и рассогласование sidecar

Принятый `project.json` — источник истины. Job file и manifest нельзя объявлять атомарной транзакцией над несколькими файлами только потому, что оба записываются через rename.

Основной вариант P1 — небольшое optional поле `operationReceipts` в manifest: список `{operationId, requestHash, revisionId}`, максимум 100 записей. Оно хранит подтверждения accepted operations и записывается **в том же commit**, что scene/assets/history. `requestHash` считается из нормализованного неизменяемого intent: целевая сцена, candidate hash, выбранные параметры и согласованный исходный контекст. Credentials, prompt, временные URLs в receipt не нужны.

Алгоритм под project lock:

1. Если тот же `operationId` найден и `requestHash` совпадает, вернуть исходную принятую revision и актуальный project state, ничего не меняя.
2. Если ID найден, но hash другой, отклонить несовместимый повтор.
3. Если ID не найден, проверить допустимость новой операции, ETag и остальные invariants; записать receipt вместе с одним commit.
4. После commit обновить sidecar job. Ошибка этого шага не отменяет принятую сцену и не разрешает удалять её source.
5. При recovery наличие receipt доказывает принятие даже после последующей правки или restore. Отсутствие receipt при изменившемся base ETag означает `acceptance_unknown`; автоматически повторно применять candidate нельзя.

Receipt не откатывается при обычном восстановлении старого take. Его история не является частью render fingerprint. Старые проекты без этого поля должны открываться и работать в новой версии. Обновить types/schema/validation/compatibility docs согласованно: старые бинарные версии со строгим `additionalProperties:false` могут отвергать новый файл, поэтому обратную читаемость новым кодом нельзя выдавать за способность старого приложения читать новые metadata.

Не требовать наличия `receipt.revisionId` в текущей ограниченной history: сто последующих обычных edits могут вытеснить эту revision раньше, чем сто новых Accept вытеснят receipt. Проверка повторного уже принятого operation выполняется до проверки старого ETag, наличия candidate и текущего содержимого целевой сцены.

Повтор после последующей пользовательской правки не должен возвращать старый candidate поверх неё. Новое применение старого candidate — новая явная операция с актуальной версией. Receipt retention имеет конечный горизонт; отсутствие удалённой старой записи не доказывает, что операция никогда не выполнялась. Unknown/stale intent требует сверки и нового явного действия, а не автоматического переиспользования ID.

Если проверка существующего формата обнаружит, что optional receipt невозможно добавить без несоразмерной миграции, зафиксировать отклонение до реализации и использовать консервативное восстановление с `acceptance_unknown`. В этом варианте нельзя обещать автоматическое распознавание каждого принятия после сбоя. Не строить ради P1 БД или распределённую транзакцию.

### 9.5. Конфликты

Целевая сцена изменена, удалена, переставлена, проект сменил aspect ratio, либо пришёл ещё один внешний edit — каждый случай проверяется при Accept, а не только при submit.

Если изменились только несвязанные сцены, допустимо принять candidate после чтения актуального проекта и проверки целевой сцены/контекста. Новая revision должна сохранить все внешние изменения. Если простой первый вариант требует повторного preview при любом ETag change, это допустимо, но UI должен объяснять причину и не зацикливаться.

После показа conflict dialog и перед commit повторно проверить версию. Решение пользователя не является бессрочным разрешением перезаписать любое последующее состояние.

### 9.6. История и лимиты

Старые accepted sources остаются в `assets/`, восстановление возвращает полную сцену. Reject не сокращает project history.

До paid submit желательно проверить, что применение candidate вообще возможно по текущим лимитам. Повторить проверку при Accept, поскольку проект мог измениться. Если свободное место исчезло, candidate сохранить и показать исправимое ограничение.

Для первой версии не повышать caps бесконтрольно. Очистка/архивирование принятой истории и референсный сборщик мусора относятся к отдельной задаче после измерения реальных проектов.

## 10. Local API, CLI и внешний агент

### 10.1. Один service, два интерфейса

UI и CLI используют одни generation/project use cases. Ошибки, duplicate protection, costs и конфликты не должны зависеть от выбранного интерфейса.

Предлагаемые операции API:

| Операция | Эффект |
| --- | --- |
| Capabilities/configuration status | Только безопасное описание доступности |
| Prepare | Локальная validation, estimate, запись подготовленного intent |
| Submit | Единственная операция запуска нового remote job |
| List/get status | Чтение state, без нового submit |
| Resume observation | Продолжение наблюдения существующего remote ID |
| Retry download | Повтор получения того же результата |
| Candidate preview | Временный render без принятия |
| Accept | Атомарная project operation |
| Reject | Решение по candidate, без потери принятого фильма |
| Stop tracking / remote cancel | Различимые действия по capabilities |

Конкретные route names и JSON schemas фиксировать перед UI. Новый `/api/generation/...` не должен путаться с существующим `/api/job` экспорта.

### 10.2. CLI-контракт

Следующие команды — **проектируемый интерфейс, в 0.1 отсутствуют**:

```text
generation capabilities
generation prepare <project.json> --request <request.json> --json
generation submit <project.json> --job <local-id> --approval <approval.json> --json
generation status <project.json> --job <local-id> --json
generation resume <project.json> --job <local-id> --json
generation download <project.json> --job <local-id> --json
generation preview <project.json> --job <local-id> --draft <draft.json> --out <directory> --json
generation accept <project.json> --job <local-id> --draft <draft.json> --preview <preview-id> --if-match <etag> --operation-id <id> --json
generation reject <project.json> --job <local-id> --json
```

`approval.json` — локальная запись разрешённых параметров/бюджета, не файл credentials. Его формат агент проектирует с тем же service, что используется UI. Это локальная защита от случайного запуска, не подписанный платёжный документ и не глобальная авторизация внешнего агента.

Добавить способ получить ETag/scene state для CLI и поддержать version check при обычных accepted edits. Не заставлять агента читать secret session URL или обходить UI auth ради локального workflow.

stdout содержит machine-readable result, stderr — прогресс. Exit code отличает завершённую команду от ошибки; успешное создание local job не означает готового видео. Для asynchronous start возвращать phase/status/IDs и следующую допустимую операцию.

### 10.3. Обновление skill

Переписать затронутые части `skills/agent-motion-studio/SKILL.md` и references:

- отдельно описать создание draft и accepted v2 edits;
- импорт/принятие через shared project API/CLI;
- video scenes, trim и сохранение type;
- generation prepare/submit/status/download/preview/accept;
- расходы и явное разрешение на новый submit;
- чтение candidate content как данных, а не инструкций;
- сохранение accepted takes и other scenes;
- пределы поддержанных clients и моделей;
- финальный отчёт с actual evidence.

Пример рабочего поручения внешнему агенту:

> Открой мой проект. Предложи более крупный план второй video scene. Подготовь запрос выбранной модели и покажи данные/расходы. После разрешённого запуска дождись кандидата, покажи preview, затем примени выбранный дубль, экспортируй и проверь остальные сцены. Сохрани возможность восстановления.

Первый client integration — существующий skill/CLI. MCP-server добавлять только после работающего CLI-контракта и конкретной необходимости. Встроенный чат не является критерием P1.

## 11. UI: конкретные состояния и действия

### 11.1. Основные элементы

1. Кнопка «Создать дубль» у выбранной video scene.
2. Панель prompt/reference и параметров модели.
3. Карточка стоимости и отправляемых данных.
4. Список jobs текущей сцены с восстановлением после reload.
5. Candidate player и preview применения.
6. Явные Accept/Reject, возврат к принятому варианту.
7. Ошибка с действием: исправить параметры, подключить key, возобновить polling, скачать результат, решить конфликт.

Состояния и текст должны помогать пользователю понять, что происходит с его фильмом. Remote IDs, hashes и implementation details помещать в раскрываемую диагностику, если они не нужны для обычного выбора.

### 11.2. Важные UX-контракты

- Генерация не требует несвязанного сохранения dirty scene без объяснения. Пользователь сначала сохраняет/отклоняет обычный draft либо явно выбирает основу запроса.
- Pending local edits и generated candidate draft не смешиваются.
- Выбор другого candidate не означает принятие.
- Переключение сцены, изменение музыки, reload и export не принимают candidate автоматически.
- Accept показывает, какая сцена изменится и какая duration останется.
- Если sound исходника игнорируется, это видно до принятия; оплачиваемый audio generation не включать без причины.
- Если frame преобразуется из другого fps/resolution, сохранить исходные параметры в provenance и показать итоговые export settings.
- Сервер возвращает ошибку независимо от UI validation; браузерные ограничения не являются единственным контролем.
- Значения prompt/provider error отображаются через безопасный text rendering.

### 11.3. Доступность и language

Для P1 достаточно согласованных с существующим UI русских подписей и понятного API. Keyboard focus, labels, disabled state и role/status должны работать у новых элементов. Не ломать текущие selectors и конфликтный dialog без обновления behavioral tests.

Английский UI и компактный language dictionary добавить как отдельную часть P2. Не тянуть UI framework ради перевода.

## 12. Безопасность новой интеграции

Это конкретные границы нового сетевого кода; они не требуют изменения модели доверия всего приложения.

### 12.1. Credentials

- Читать секреты в Node process, не из публичного project JSON.
- Не передавать их в browser, URLs, CLI arguments, provider-independent log context или exports.
- Не включать session cookies/tokens в screenshots и отчёты.
- Не хранить Claude/ChatGPT чужие session files и не извлекать tokens из установленных клиентов.
- Для P1 env-based configuration достаточно; secret manager/UI key entry не обязательны.
- Public status endpoint сообщает наличие конфигурации, но не значение и не часть секрета.

### 12.2. Сеть и reference uploads

- Существующий studio server остаётся loopback с Host/Origin/session checks.
- Для long-running jobs использовать polling; не открывать inbound webhook или публичный tunnel ради первой модели.
- Production provider origins и upload/result hosts берутся из проверенного adapter contract.
- Произвольные URLs из prompt не становятся адресами для fetch.
- Проверять scheme, host, port, credentials in URL и redirects.
- Не объявлять hostname allowlist полноценной защитой от DNS rebinding. Выбрать проверенный transport, контролирующий конечные IPv4/IPv6 адреса и запрещающий loopback/private/link-local/metadata для удалённого provider download, либо документированно ограничить транспорт фиксированными доверенными endpoints.
- Test server на loopback подключается только через dependency injection тестов. Production base URL не подменяется пользовательским prompt или публичным request field.
- Если добавленный provider требует пользовательский arbitrary storage URL, это отдельное решение с отдельной проверкой; default P1 — официальный upload flow.

### 12.3. Файлы и процессы

- Candidate/job IDs валидируются; они не являются произвольными filesystem paths.
- Проверять realpath containment, symlink/junction escapes и новый output path через проверенного родителя.
- Не передавать provider filenames в shell command text.
- FFmpeg запускается массивом аргументов с `shell:false`; inputs только проверенные локальные files.
- Ограничить bytes, duration, geometry и execution time до дорогого decode.
- Cleanup удаляет только созданные текущей операцией временные файлы внутри проверенного workspace.
- Не рекурсивно удалять вычисленный каталог без проверки абсолютного target.

### 12.4. Logs и публичные материалы

Хранить стадии, длительности, counts, normalized error codes и безопасные IDs. Raw response bodies, authorization headers и signed query strings по умолчанию не логировать. Ошибки SDK могут содержать URL/headers: нормализовать их до UI/JSON report.

Проверять состав source/runtime/demo archives. Public docs используют переносимые относительные пути и ссылки на поставляемый материал. Private jobs, source references пользователя и consent records не распространяются автоматически.

## 13. Матрица проверки P1

### 13.1. Принцип

Тесты проверяют эффекты: число POST, содержимое сохранённого проекта, history, реальные кадры, hashes и поведение UI после restart. Проверка наличия полей/строк сама по себе не доказывает работающую интеграцию.

Controlled provider в tests должен использовать настоящий локальный HTTP server или эквивалентный transport с журналом запросов и управляемыми задержками. Он проверяет наш contract, но не поведение удалённого сервиса.

## 14. Реальная генерация и независимое подтверждение

### 14.1. Готовность к платному/онлайн запуску

До запроса разрешения должно быть что проверить: код adapter, offline tests, работающий UI, подготовленный request и описание расходов. Реальная интеграция не должна начинаться с набора ручных HTTP команд без сохранения job в приложении.

Если live-run ещё не разрешён, отчёт содержит:

- выбранную модель и reason;
- конкретный mode/duration/resolution;
- reference, который предлагается отправить;
- estimate и число запросов;
- где безопасно настроить key;
- какие offline проверки уже прошли;
- точный оставшийся live acceptance шаг.

После получения недостающих данных продолжать от сохранённого состояния. Не повторять все исследования и не заново запрашивать уже выданное разрешение.

### 14.2. Сценарий live verification

1. Сохранить исходную revision, hashes sources и базовый export контрольного фильма.
2. Подготовить один запрос в UI/CLI тем же production code path.
3. Запустить один generation job в пределах разрешения.
4. После получения remote ID перезапустить сервер/UI и возобновить наблюдение этого ID.
5. Скачать и проверить output.
6. Посмотреть actual generated clip и preview применения, записать наблюдаемые ограничения.
7. Принять candidate явным действием.
8. Экспортировать изменённый фильм.
9. Сравнить неизменные сцены по decoded frames; при неизменной duration сравнивать соответствующие интервалы.
10. Восстановить предыдущую сцену и снова экспортировать.
11. Сравнить restored film с исходным в том же окружении, проверить hashes всех старых sources.
12. Открыть переносимую локальную копию проекта без ключа и без remote URLs.

Если провайдер завершает слишком быстро для настоящего pending restart, честно записать: live job проверен, in-flight restart проверен только controlled test. Не выдавать restart после готового clip за возобновление активного inference и не делать дополнительную платную генерацию без оставшегося разрешения.

### 14.3. Evidence

Сохранить локально:

- brief/request snapshot без secrets;
- provider/model/settings и дату;
- переходы states и count submit;
- elapsed time: submit, queue, inference при доступности, download, preview, export;
- estimate и известные actual costs отдельно;
- original/changed/restored MP4;
- hashes sources и decoded-frame comparison;
- logs и exit codes;
- что просмотрено глазами/прослушано, кем и в каких пределах;
- список NOT RUN.

Настоящий клип может оказаться художественно непригодным. Это не провал программного сохранения/restore, но такой результат нельзя называть доказательством качества AI-студии. Отчёт разделяет technical completion и visual acceptance.

## 15. Разбиение P1 на небольшие изменения

Ниже — порядок implementation slices. Это не требование создать столько публичных PR; каждую часть можно проверить локально, а публикация выполняется отдельно по поручению.

| Часть | Изменения | Приёмка перед следующей частью |
| --- | --- | --- |
| 01. Baseline/decision | Source audit, provider decision, request/response contract | Известны поддержанные параметры и ограничения |
| 02. Local job lifecycle | Store, locks, prepare/submit/status/restart с controlled transport | J01–J16 в релевантном объёме, actual POST counts |
| 03. Production adapter | Один documented provider, explicit auth/costs | Adapter contract покрыт, production не подменяется fake |
| 04. Candidate media | Download/validation/storage | D01–D10, candidate не меняет accepted manifest |
| 05. Preview и Accept | Shared preview, project transaction, receipt/recovery | A01–A06, A13–A19 |
| 06. UI | Generation panel, candidates, conflicts, reload | A07–A12 через настоящий browser |
| 07. CLI/skill | Те же operations, machine-readable results, v2 guidance | Один внешний agent workflow без direct accepted writes |
| 08. Packaging и review | Docs, ignore/audit, installed consumer | S01–S06, package работает вне checkout |
| 09. Live acceptance | Один разрешённый remote job и film replacement | Раздел 14 с реальными артефактами |

Небольшой вертикальный сквозной путь допустим раньше полной UI-полировки: prepare → controlled job → candidate → accept → render. Не тратить весь этап на абстрактный provider framework без получаемого результата.

Если независимые агенты помогают, распределять по зонам: provider/store, UI после фиксированного контракта, read-only review/tests. `project.ts`, API schemas и accepted semantics имеют одного владельца изменения. Общие media tests запускает один координатор.

## 16. P2: удобство, фильм из задания и внешний агент

Основной brief-to-film и внешний агент перенесены в A1 (§1.5) и не ждут платного P1 live-run. Этот раздел описывает дальнейшее улучшение удобства после первого подтверждённого агентного сценария.

### 16.1. Первый запуск

Подготовлены [последовательная инструкция](../../GETTING_STARTED.md), [продолжение проекта](../../AGENT_WORKFLOW_RU.md) и [независимая проверка](../../USER_TRIAL_RU.md). Исправлено препятствие doctor: отсутствующий браузер больше не скрывает состояние FFmpeg/ffprobe; ошибки содержат способ исправления. English UI, clean-machine setup и независимый участник остаются открытыми.

- Понятный launch/open/create project flow.
- Диагностика отсутствующего Node/Chrome/FFmpeg с конкретным исправлением.
- English/Russian UI и одинаковый смысл состояний.
- Guided first remix со своим материалом.
- Возможность безопасно повторно открыть проект после закрытия приложения.
- Проверка на компьютере, где dependencies не были заранее настроены разработчиком.

Сначала упростить текущий launcher и инструкции. Выбор Electron/Tauri/другой desktop packaging делать по измеренным проблемам; он не должен автоматически вести к переписыванию интерфейса.

### 16.2. Brief → storyboard

Добавить редактируемую структуру film brief и shot plan:

- назначение, длительность, aspect ratio;
- главный объект/персонаж и разрешённые references;
- список сцен: смысл, действие, камера, ритм, duration;
- какие сцены используют готовые материалы, какие требуют generation;
- estimated budget и предел попыток;
- общий style/reference context.

Сначала storyboard может создавать внешний агент и передавать его как draft. Принятый фильм не заполняется фиктивными generated assets. Создание новых video scenes и замена type требуют явных domain operations с тестами, а не обхода `patchScene`.

### 16.3. Режиссёрские настройки

Выбрать несколько понятных пресетов для одной модели и задачи. Каждый preset должен соответствовать документированным параметрам или честно обозначенному prompt template.

Проверить на одинаковых references/settings несколько результатов: заметно ли действие пресета, стабилен ли объект, сколько дублей пригодны. Не обещать физически точную камеру и character consistency только по названию кнопки.

### 16.4. Независимая пользовательская проверка

Первый внешний участник получает README и приложение без implementation context. Его не заменяет второй агент, унаследовавший всю историю разработки.

Записать:

- смог ли установить и открыть проект;
- время до первого preview/export;
- где потребовалась помощь;
- число генераций и пригодных дублей;
- смог ли изменить только нужную сцену;
- понял ли расходы и различие candidate/accepted;
- удалось ли восстановить и передать проект;
- захотел ли использовать со своим следующим материалом.

Для планирования можно начать с одного участника, затем нескольких независимых попыток. Это предложенный размер исследования, не уже полученные пользователи. Публикация и отправка приглашений выполняются только по разрешению человека.

## 17. P3: измеренная оптимизация локального рендера

### 17.1. Baseline производительности

Зафиксировать один контрольный проект и окружение. Измерять отдельно:

- cold full export;
- повтор без изменений;
- изменение только второй сцены;
- изменение только музыки;
- изменение duration, меняющее global timing;
- scene preview;
- пик RAM, disk use и временные files;
- число browser launches и encodeScene вызовов.

Использовать одинаковые settings и последовательные запуски. Хранить отдельные cold/warm измерения и несколько повторов; не выдавать единственный удачный warm run за общий speedup.

### 17.2. Кэш по сценам

После measurement внедрить reusable encoded segments. Cache key учитывает:

- реальные content hashes sources;
- scene fields и длительность;
- aspect/resolution/fps/pixel/color settings;
- trim, fit, focal point;
- используемые brand/style/font/renderer versions;
- seed и временной контекст, от которого зависят пиксели;
- encoder settings и релевантные software versions.

Текущие motion frames используют global frame position; перемещение/изменение предыдущей duration может требовать cache invalidation даже при прежнем scene JSON. Нельзя считать scene ID достаточным ключом.

Final audio mix и concat имеют отдельные зависимости. Замена музыки не должна требовать повторной генерации AI-клипов. Cache entry публикуется только после verification; damaged cache даёт miss и пересборку. Параллельные процессы не должны считать неполный segment готовым.

Критерий: после изменения одной независимой сцены повторно кодируется только необходимое; итоговое видео проходит media tests и сравнение с cache-disabled render. Зафиксировать реальное ускорение и disk cost без обещанного заранее коэффициента.

### 17.3. Лёгкий preview

Ввести меньшую геометрию preview только при измеренной необходимости. Пользователь видит, что это предварительное качество. Геометрия/trim/timing следуют общему encoder path; сравнивать с full export с учётом масштаба, а не требовать невозможной побитовой идентичности разных разрешений.

Точный preview P1 сохраняется как reference или отдельный режим. Не называть lower-resolution thumbnail полной проверкой финальных титров.

### 17.4. Остальные оптимизации

После profiling рассмотреть уменьшение PNG I/O, повторное использование браузера и hardware encoding. Менять по одной причине и измерять эффект.

Hardware encoder имеет fallback на проверенный software path. Его output может отличаться по пикселям/размеру/качеству: ввести отдельные заранее определённые quality checks и не переносить byte-equality ожидание без анализа.

Оптимизация рендера не меняет провайдерные счета за уже выполненный inference. Расходы сокращаются отдельно: reuse takes, generation только нужных сцен и отсутствие duplicate submissions.

## 18. P4: дополнительные способы генерации

### 18.1. Второй облачный provider

Добавлять после первого независимого использования, когда понятна причина: недоступность региона/аккаунта, другой mode, качество или стоимость. Повторно использовать проверенный lifecycle; не расширять контракт по рекламному каталогу заранее.

Два providers могут иметь разные durations, prices, seed semantics, audio и cancel. UI отображает реальные capabilities, а не общий набор переключателей, половина которых игнорируется.

### 18.2. Официальные subscription integrations

Выбирать один конкретный маршрут, документировать доступность и ownership аккаунта. Подписка агента и подписка видеогенератора — разные ресурсы.

OAuth integration требует PKCE/state, secure storage, refresh/revoke, account switching и отдельной проверки provider terms. Если текущий внешний агент уже умеет авторизоваться в официальном MCP, не дублировать весь auth flow ради первой демонстрации.

Не предлагать пользователю копировать browser cookies, session tokens или credentials другого установленного приложения.

### 18.3. Локальная видеомодель

Порядок:

1. Выбрать одну модель/revision/workflow с допустимой лицензией.
2. Определить целевой GPU/VRAM/RAM/диск/ОС и реальный доступный test machine.
3. Проверить first-run, скачивание весов и local dependencies как отдельный пользовательский опыт.
4. Получить реальный короткий clip; измерить время и память.
5. Подключить backend к тому же candidate/accept/restore workflow.
6. Проверить interrupted job, повторное открытие и output validation.
7. Указать, что resume observation не всегда означает продолжение inference с последнего вычисленного шага.

Исходные точки исследования: [Wan2.1](https://github.com/Wan-Video/Wan2.1), [Wan2.2](https://github.com/Wan-Video/Wan2.2), [LTX Desktop](https://github.com/Lightricks/LTX-Desktop). Проверять конкретные licenses кода и weights отдельно. Не считать популярный checkpoint свободным для конкурентного продукта без чтения его условий.

В исходном аудите этого компьютера обнаружена AMD Radeon 780M; работоспособность CUDA-oriented inference на нём не подтверждена. Не скачивать большие weights и не обещать поддержку по одному наличию GPU. При отсутствии подходящего оборудования local backend остаётся неподтверждённым, а cloud/BYOK workflow продолжает быть полезным.

### 18.4. Хранение и очистка

Когда реальные projects упрутся в caps/storage, спроектировать архивирование и явную очистку. Считать ссылки текущих scenes, history, accepted receipts и переносимых пакетов. По умолчанию сохранять пользовательскую работу; garbage collection не должен удалять принятые takes ради места для нового candidate.

## 19. P5: переносимость и готовность к стабильной версии

### 19.1. Формат переносимого проекта

Экспортируемый editable project содержит manifest и все необходимые локальные assets. Не включать credentials, session links, runner locks и signed provider URLs.

Предлагаются явно названные варианты, если они понадобятся:

- полный проект с сохранённой accepted history и всеми её sources;
- облегчённая копия только текущего монтажа, создаваемая отдельным действием с понятным предупреждением о неперенесённой истории.

Нельзя удалить history sources и назвать результат полной редактируемой копией. Generation provenance можно включать в очищенный отдельный metadata-файл по явному выбору; prompts тоже могут быть приватными.

### 19.2. Package и новая установка

Проверить исходный ZIP и runtime archive в новом каталоге вне checkout:

- installation без доступа к `src`, local references и `.agents`;
- doctor/init/open;
- обычный edit/preview/export;
- generation status/ready candidate/accept там, где предусмотрены fixtures;
- отсутствие случайного live submit во время package smoke;
- наличие schema, fonts, UI assets и новых modules;
- portable docs links;
- paths с пробелами и нелатинскими символами.

Установка в новом каталоге на том же компьютере не равна clean OS setup. Отдельно зафиксировать уже установленные system dependencies.

### 19.3. Release gates

Перед будущей публикацией:

- актуальные проверки source/unit/media;
- production adapter live verification с разрешением и известными границами;
- installed consumer;
- secret/distribution/link audit;
- актуальный CI результат;
- release notes и compatibility matrix;
- hashes подготовленных архивов;
- права на distributed media;
- отдельное разрешение на push/tag/release/upload, если его ещё нет.

Повышение версии должно обновлять package/lock/release notes/check scripts согласованно. Не менять `private:true` и registry policy попутно с feature.

## 20. Команды проверки и порядок запуска

### 20.1. Уже существующие команды

```powershell
npm run check
npm run doctor
npm run test:integration
npm run check:release
npm run release:prepare
npm run verify:package
```

`release:prepare` и `verify:package` выполнять последовательно: вторая использует подготовленный package. Они готовят/проверяют локальную поставку; это не публикация.

Для docs-only изменения достаточно `npm run check:release` и проверки diff. Для project/server/studio/renderer изменений выполнить `npm run check` и `npm run test:integration`. Optional Edge/Windows console tests запускать при изменении соответствующих частей или отдельном поручении, не включать онлайн-вызовы в default suite.

### 20.2. Будущие тестовые команды

Агент может добавить, например, `test:generation` для offline contract/UI/media tests. Имя и состав записать в package scripts. Нельзя документировать её как существующую до реализации.

Live verification вынести в отдельный явный script с требуемыми key/budget/request inputs. Не запускать live tests из `npm test`, `check`, default integration, install hooks или GitHub CI по умолчанию.

### 20.3. Что считать достаточной проверкой

После релевантных зелёных tests и завершённого сценария не повторять полный suite без нового изменения, failure или нерешённого риска. Не тратить бюджет на одинаковые рендеры ради увеличения числа проверок.

## 21. Отчёт агента и передача следующему исполнителю

### 21.1. Короткий статус

Использовать точный статус:

- **Работает локальный contract; live provider не проверен.**
- **Настоящая генерация проверена; пользовательский workflow ещё неполон.**
- **Полный P1 проверен на указанном provider/окружении.**
- **Есть конкретный blocker**, с причиной и сохранённым воспроизведением.

Не использовать общий «готово», если выполнена только часть acceptance.

### 21.2. Обязательное содержимое финального отчёта

1. Какой пользовательский результат теперь возможен.
2. Что изменено и какие domain invariants сохранены.
3. Provider/model и scope подтверждённой интеграции.
4. Команды, exit codes, passed/failed/skipped.
5. Какие media/UI scenarios выполнены реально.
6. Live submit count, известные расходы и ограничения измерения.
7. Links к local artifacts, без secrets.
8. NOT RUN и оставшиеся риски.
9. Как запустить, продолжить job, принять candidate и восстановить take.
10. Ближайший следующий шаг с конкретным критерием, без автоматического расширения scope.

### 21.3. Машиночитаемая evidence запись

Можно сохранить `artifacts/<run-id>/verification.json` со следующими группами:

```json
{
  "scope": "P1 generated replacement shot",
  "commit": "actual checked commit",
  "workingTreeChanges": "record actual diff state",
  "environment": {},
  "commands": [],
  "offlineCases": [],
  "liveProvider": {
    "status": "not-run",
    "reason": "record actual reason",
    "submitCount": 0
  },
  "artifacts": [],
  "notRun": [],
  "knownLimits": []
}
```

Это шаблон отчёта, не доказательство выполнения. Значения заменяются фактическими результатами; пустые fields нельзя выдавать за пройденные проверки.

### 21.4. Продолжение после смены агента

В локальной передаче указать:

- текущий этап и acceptance status;
- ветку/commit и незакоммиченный diff;
- какие файлы менялись и что принадлежит пользователю;
- выбранный provider contract и ссылки;
- безопасный local job ID, статус и следующую допустимую операцию;
- уже выданные пользователем разрешения и оставшийся бюджет, без секретов;
- последнюю выполненную команду и результат;
- что не повторять, чтобы не создать duplicate paid job;
- точный незакрытый тест/вопрос.

## 22. Критерий завершения ветки video API

Работа P0–P1 в дополнительной ветке video API завершена, когда:

- выбран и документирован один официальный video provider;
- production path не подменяется mock;
- request/cost/reference видны до submit;
- job сохраняется и продолжает наблюдение после restart;
- неопределённый submit не повторяется слепо;
- candidate скачан и проверен;
- candidate preview не меняет принятого проекта;
- Accept атомарно меняет одну video scene и сохраняет предыдущую;
- конфликт с внешним edit проверен через настоящий UI;
- export/restore и сохранность sources подтверждены;
- CLI/skill и UI используют один контракт;
- package/документация соответствуют реализации;
- состоялся разрешённый live-run либо финальный статус явно ограничен отсутствием этой проверки.

Если media live-run не разрешён, подготовительный объём P1 может быть завершён, но **живой video-provider workflow остаётся непроверенным**. Для его закрытия нужен разрешённый реальный запрос. Основной A1 через пользовательского агента и локальный renderer при этом продолжается независимо.

Проверка независимым человеком относится к основному A1 и дальнейшему P2. Её не следует откладывать только из-за отсутствия ключа видеопровайдера. Продолжение разработки должно опираться на фактические затруднения, качество результата и измеренные задержки.
